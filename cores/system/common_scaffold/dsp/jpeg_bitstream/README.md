# JPEG entropy byte packer

`jpeg_entropy_bitpacker.sv` accepts an already selected Huffman code and its
additional amplitude bits. It appends both most significant bit first, emits
complete entropy bytes, and inserts `00` after every entropy `FF` byte. Unflushed
partial bytes remain buffered across symbols and blocks. Input is not an entire
JPEG file, and this module does not choose Huffman codes or insert headers,
restart markers, SOI or EOI.

Inputs `s_code` and `s_amplitude` are right-aligned. Their lengths are 1..16
and 0..16, respectively, and unused high bits must be zero. Length zero for
the code is allowed only for an empty flush token, with zero amplitude/length.
Invalid accepted tokens pulse `input_error` and leave all previously buffered
bits unchanged. Codebook/prefix legality is the preceding lookup's responsibility.

`s_flush` pads the final partial byte with ones, drains all entropy and stuffing
bytes, and pulses `flush_done` after the last byte is consumed. It can accompany
a final coded symbol or be sent as a subsequent empty token. `m_last` marks the
last byte generated by that flush, including a stuffing zero if applicable.
An empty, already aligned flush produces no bytes and no last marker, but still
produces `flush_done`. Do not flush between ordinary JPEG blocks. Before inserting
an RST marker, flush entropy and wait for `flush_done`; emit the marker externally,
without entropy stuffing, and reset the DC predictor in the symbols stage.

The common transfer condition is **ce && valid && ready** on the rising edge;
both sides must share CE. Payload/valid/last are stable during stalls or CE pause.
Diagnostics are enabled-cycle pulses. Async active-low reset aborts all pending
bits/output and clears diagnostics. `pending_bits` includes buffered bits but not
a byte already presented at the output. This serial implementation finishes
draining complete bytes from one token before accepting the next.

Reference behavior was checked against
[libjpeg-turbo jchuff.c](https://raw.githubusercontent.com/libjpeg-turbo/libjpeg-turbo/main/src/jchuff.c):
the source explicitly specifies FF→FF00 and filling partial bytes with ones.
No implementation was copied. The numerical oracle uses Python bit strings,
independent of the RTL's shifted reservoir.

```powershell
python -B cores/system/common_scaffold/dsp/jpeg_bitstream/run_tests.py
python -B cores/system/common_scaffold/dsp/jpeg_bitstream/synth.py
```

335 tokens produce 700 exact bytes, including long FF sequences, mixed bit
lengths, aligned/unaligned/empty flushes, six rejected malformed tokens,
random source gaps/CE/backpressure, stable paused output and reset of a partial
segment. Logs and RTL hashes are retained in unique evidence folders; vectors
and executables are automatically removed. Isolated Gowin synthesis passes
`check -assert`: 1113 LUT1..4, 76 MUX2_LUT5, 88 FF, zero DSP/RAM. No P&R,
board, JPEG file interoperability or continuous-video rate is claimed here.
