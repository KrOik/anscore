# bresenham_step

Bresenham line rasteriser, one pixel move per accepted beat, all eight octants, decision-parameter arithmetic only (accumulate, compare, subtract, shift) so the cone holds no multiply and no divide. A program beat is c[31]=1 with a[7:0]=x0, a[15:8]=y0, b[7:0]=x1, b[15:8]=y1 and a[31:16]=b[31:16]=c[30:1]=0; it plots the start pixel and derives dx=|x1-x0|, dy=|y1-y0| by compare-then-subtract, the major length maj=max(dx,dy), the minor length min=min(dx,dy), the steep flag and the two axis signs, and clears the decision parameter. A step beat is c[31]=0 with a[31:8]=0, b=0, c[30:1]=0; a[7:0] is an operation tag echoed to aux[7:0]. Each step does err=err+min, subtracts maj once when err>=maj, moves the major axis by one always and the minor axis by one on that subtract, so after maj steps exactly min minor moves have happened and the endpoint is hit with no accumulated rounding. Fault (result=aux=0, state kept): a reserved input field is nonzero, or a step arrives before a program or after the primitive completed. State: 11:0 x, 23:12 y, 24/25 the x/y direction bits, 26 steep, 27 started, 28 done, 39:32 maj, 47:40 min, 57:48 the decision parameter, 65:58 steps taken, 68 major moved on the last beat, 69 minor moved on the last beat. result[11:0]=x, [23:12]=y, [24]=major moved, [25]=minor moved (a diagonal beat sets both), [28:26]=octant as {steep,y-dir,x-dir}, [29]=the decision parameter is in the upper half of its cell (2*err>=maj), [30]=primitive complete, [31]=degenerate line (maj=0, one pixel). aux[7:0]=tag, [15:8]=steps taken, [27:16]=decision parameter, [28]=started, [29]=done, [30]=this beat programmed the primitive, [31]=exact tie (2*err==maj).

See [common interface](../../doc/INTERFACE.md). Latency: 1 enabled edge(s); II=1 when output ready. Independent lanes per accepted beat: 1. Only accepted transactions update state. Reset clears pending output and state, even while CE is zero.

Hardware advantage: A firmware Bresenham step is a load, an add, a compare, a subtract and two branch-target updates per pixel, so the plot rate is set by the loop, not by the fabric; this core retires one pixel every enabled beat at II=1 with the whole eight-octant decision in hardwired add/compare logic, giving a line of N pixels in exactly N+1 beats and deterministic per-line latency for vector OSD and waveform plotting.

Independent integer model: `step("bresenham_step", a, b, c, state)` in tools/fam_video.py. Vector rows: 320, of which 128 run on the board. Board-set coverage: 125 distinct responses, 4 fault rows.
